# AI 售后工单辅助台

面向电商商家的售后问答辅助工具：把客户问题拆成**诉求 / 已知事实 / 信息缺口 / 争议点 / 处理建议与依据 / 不确定性**六块，并明确标出**什么时候不能让 AI 自己回答**。

> 这是个人项目，用于演练与求职展示。规则为模拟规则，**不代表任何真实商家的售后制度**，未经真实商家验证、未上线、没有真实用户。

## 现在是什么状态（V3-2，2026-11-21）

**核心不是「生成一段客服话术」，而是「说清这个售后问题现在能确认什么、还缺什么、下一步怎么处理」。**

| 层 | 文件 | 作用 |
|---|---|---|
| 结构化分析 | `analysis.py` | 把一句话 + 规则命中拆成六个模块；事实带来源，缺口分「必须 / 可选」，只报真实出现的矛盾 |
| 单轮补充再分析 | `analysis.py::_diff_reports` | 客户补充信息后重新分析，并说清「这次补充改变了什么」 |
| 识别第 1 层 | `engine.py::_analyze_v1` | 15 条关键词规则；客户原话命中权重是辅助字段的 2 倍 |
| 识别第 2 层 | `llm_classifier.py` | 模型只做意图分类与事实抽取，不写答复；编造规则 ID 归 UNKNOWN |
| 识别第 3 层 | `engine.py::SYNONYMS` | 无密钥 / 模型失败时兜底 |
| 识别第 4 层 | `engine.py::FOLLOW_UP_QUESTION` | 转人工时附一句可直接发出的澄清话术 |

- 规则库：5 类 × 15 条 + 12 个转人工触发词
- 界面：Streamlit，侧边栏可切 auto / rules / llm
- 命令行：`main.py`，默认输出结构化报告，`--brief` 看简版

## 三条产品底线（写进代码，不靠自觉）

1. **已知事实只能来自输入或模型抽取**，每条标来源与核实状态；不生成订单号、物流单号、凭证、金额。
2. **依据只能来自规则库**；规则没覆盖就不给结论，而不是编一条规则。
3. **没发现争议就明说「暂未发现明显争议」**，不为了看起来完整而编一个争议；有矛盾时两边都摆出来，交人工核实。

## 输出只有四类，没有第五类

1. **规则明确 + 信息齐全** → 给处理建议与规则依据
2. **关键信息缺失** → 标出缺什么，区分「必须核实 / 可选补充」，不硬答
3. **双方说法冲突** → 两边都摆出来，交人工核实，不替任何一方下结论
4. **赔付 / 投诉 / 例外承诺 / 规则未覆盖** → 转人工，AI 不独立担责

设计意图：宁可少答，不可乱答。测试里「转人工」不算失败，**错误答复才算**。

再做三条：平台规则优先于商家规则、不假装引用未提供的规定；不连接电商后台、不自动查询订单物流、不自动退款；测试材料优先用虚构或脱敏案例。

## 测试现状（数字都是跑出来的）

| 测试 | 命令 | 结果 |
|---|---|---|
| 结构化验收（六模块 / 不编造 / 缺口分级 / 争议 / 补充再分析） | `python tests\test_structured.py` | **81/81** |
| 12 条设计用例（不回退） | `python tests\run_tests.py` | **12/12** |
| 6 条换说法（分层判定） | `python tests\run_badcases.py` | rules **0/5 命中 + 1/1 正确转人工**；llm **5/5 + 1/1**；错误答复 **0** |
| 模型层单测（假客户端） | `python tests\test_llm_parse.py` | **10/10** |
| 页面冒烟（Streamlit AppTest） | `python tests\test_app_smoke.py` | **10/10** |

诚实说明：

1. 12 条设计用例是照着规则关键词写的，属于「自己出题自己答」，只证明实现与设计一致。
2. 换说法测试分三类判定：规则用例必须给对规则、转人工用例必须转人工、给错结论算错误答复。不合成一个「命中率」。
3. **N6「能不能便宜点」按「转人工、不承诺优惠」处理**（讲价 ≠ 价保）。模型判 UNKNOWN 是对的，原先是用例期望写错。
4. 同义词表包含测试句的说法，所以命中率不能当泛化能力证明。
5. 「事实抽取」在没有密钥时只依赖输入字段；有密钥时调用模型抽取，结果标「模型抽取 · 待核实」。
6. 客户已提供的证据（照片/截图/视频、单号）不再列为缺口，但仍靠关键词识别，说明「凭证在聊天里」这类说法认不出。

## 怎么运行

**方式一（最省事）**：直接双击 `run.bat`。它会自动用项目自带的 `.venv`（依赖已装好），浏览器会打开页面。

**方式二（PyCharm）**：File → Open → 选 `D:\AI售后辅助` → 打开，然后在底部 Terminal 执行
```
python -m streamlit run app.py
```

**方式三（命令行，最快）**：
```
python main.py --check                          # 三步体检：库、密钥、密钥能不能用
python main.py --open-env                       # 帮你打开 .env 填密钥
python main.py "我买的东西还没发货，我想退款"     # 结构化报告
python main.py "东西坏了" --补充 "1号签收的，照片已发"   # 补充信息后重新分析
python main.py --brief "东西坏了"                # 简版输出
python main.py --rules "东西不满意，能退钱吗"     # 只跑关键词，看 V1 原样
```

**配模型密钥（可选，不配也能用，只是跳过模型层）**：三种方式挑一个。

方式 A · 只在当前终端（不建文件，关掉窗口就没了）：

```powershell
Set-PSReadLineOption -HistorySaveStyle SaveNothing   # 本窗口不写命令历史，密钥不落盘
$env:DEEPSEEK_API_KEY = "sk-你的真实密钥"
python main.py --check
```

> 只对这一个终端窗口有效。新开终端、重启 PyCharm、双击 `run.bat` 都读不到，工具会自动跳过模型层（不会报错）。

方式 B · 一次性永久（写进用户环境变量，双击 `run.bat` 也能用）：

```powershell
Set-PSReadLineOption -HistorySaveStyle SaveNothing
setx DEEPSEEK_API_KEY "sk-你的真实密钥"
```

> `setx` 对**当前**窗口不生效，要新开一个终端再跑 `python main.py --check`。撤销：`setx DEEPSEEK_API_KEY ""`。

方式 C · `.env` 文件（换电脑、给别人演示最省心）：

1. 跑 `python main.py --open-env`（没有 `.env` 会自动从 `.env.example` 复制一份并打开）
2. 把密钥贴在 `DEEPSEEK_API_KEY=` 的等号后面，不加引号、不留空格
3. `Ctrl + S` 保存，再跑 `python main.py --check`

`.env` 已被 `.gitignore` 排除，不会被推上 GitHub。

## 已知问题

1. **争议检测是规则化匹配**：只覆盖 4 类「客户说法 vs 订单情况」矛盾，复杂对话冲突还认不出。
2. **缺口分级是启发式**：含「单号 / 时间 / 状态 / 凭证」等关键词的项算「必须核实」，不是按业务影响排的优先级。
3. **答复建议仍是规则库原文**：客户已提供凭证时，建议里那句「请客户提供照片/视频」不会自动改写，只额外附一条「跳过索要凭证」的提示。彻底解决要在规则里做「已有凭证」变体文案。
4. **证据识别靠关键词**：只认照片 / 截图 / 视频 / 单号，客户说「凭证我发在聊天里了」这类说法认不出。
5. 同义词表有天花板，且与测试句有重叠，命中率偏乐观。
6. 6 条换说法样本太小，模型真实水平要用 20 句真实客服用语验证。
7. **补充信息只支持单轮**：再补一次就会覆盖上一次（不保存历史、不做多轮状态）。这是有意的取舍。
8. **「补齐缺口」靠人工别名表**：`analysis.GAP_ALIASES` 里登记了每条缺口对应的说法，没登记的说法认不出，会让缺口看起来还在。「XX 时间」这类缺口额外要求补充信息里真的出现时间，避免「已签收」被当成「签收时间已补齐」。
9. 没有用户测试、没有部署、没有真实客服对话验证。
