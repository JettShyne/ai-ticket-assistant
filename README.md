# AI 售后工单辅助台

面向电商商家的售后问答辅助工具：把客户问题归类，给出**答复建议 + 规则依据**，并明确标出**什么时候不能让 AI 自己回答**。

> 这是个人项目，用于演练与求职展示。规则为模拟规则，**不代表任何真实商家的售后制度**，未经真实商家验证、未上线、没有真实用户。

## 现在是什么状态（V2，2026-11-21）

- **三层识别**：关键词规则 → 大模型意图分类 → 同义词兜底 → 转人工
- 规则库：5 类 × 15 条 + 12 个转人工触发词
- 核心设计：**模型只判断「客户在说什么、缺什么信息」，答复与依据仍由规则库给出**，避免模型编造规则、乱承诺赔付
- 界面：Streamlit 页面（客户消息 + 商品类型 + 订单情况 → 分类、建议、依据、待确认信息、澄清话术）
- 命令行：`main.py`，支持 `--rules / --llm / --auto` 三种模式对照

## 测试现状（数字都是跑出来的）

| 测试 | 结果 | 说明 |
|---|---|---|
| 12 条设计用例 `tests/run_tests.py` | **12/12 通过** | 保证 V2 没有回退 V1 的能力 |
| 6 条换说法用例 `tests/run_badcases.py` | rules **0/6** → auto **6/6** | auto 的命中来自同义词层；模型层因未配密钥未参与 |
| 分层单元测试 `tests/test_llm_parse.py` | **9/9 通过** | 用假客户端验证「模型返回解析、编造 ID 拦截、失败回落」逻辑 |

诚实说明两点：

1. 12 条设计用例是照着规则关键词写的，属于「自己出题自己答」，只能证明实现与设计一致。
2. 同义词表是按意图整理的，**里面包含测试句的说法**，所以 6/6 不能当作泛化能力证明。泛化必须用真实客服用语验证（见下）。

## 怎么运行

**方式一（推荐）**：双击 `run.bat`，浏览器自动打开。

**方式二（PyCharm）**：打开本项目，在终端执行
```
python -m streamlit run app.py
```

**方式三（命令行，最快）**：
```
python main.py --check                          # 先确认模型层是否就绪（不显示密钥）
python main.py "东西不满意，能退钱吗"            # auto：规则 → 模型 → 同义词
python main.py --rules "东西不满意，能退钱吗"    # 只跑关键词，看 V1 原样（会转人工）
python main.py --llm "东西不满意，能退钱吗"      # 规则 + 模型，禁用同义词
```

**配模型密钥（可选，不配也能用，只是跳过模型层）**：

1. 把 `.env.example` 复制一份，改名成 `.env`（开头有个点）
2. 用记事本打开 `.env`，把 `sk-在这里填你自己的密钥` 换成你自己的 DeepSeek 密钥
3. 保存，再跑 `python main.py --check`，出现「模型调用层：可用」就成了

`.env` 已被 `.gitignore` 排除，不会被推上 GitHub。

## 产品边界（这是重点）

输出只有三类，没有第四类：

1. **规则明确 + 信息齐全** → 给答复建议与依据
2. **关键信息缺失** → 提示补充，不硬答
3. **赔付 / 投诉 / 例外承诺 / 规则未覆盖** → 转人工，AI 不独立担责

设计意图：宁可少答，不可乱答。测试里「转人工」不算失败，**错误答复才算**。

模型层的失败策略同样遵守这条：没有密钥、超时、返回不是 JSON、规则 ID 不存在 → 一律回落到规则与同义词，不因模型出错就给出没依据的答复。

## 已知问题

1. **同义词表有天花板**：按意图人工维护，场景越多人越累；且本次测试句与表内说法有重叠，命中率偏乐观。
2. **模型层还没有真跑过**：本机没有配密钥，模型路径只用假客户端验证了解析与回落，真实分类准确率仍未知。
3. 「主动追问」目前只是**给客服一句澄清话术**，还没有做成多轮对话。
4. 规则未接入否定、多意图混合、长对话上下文。
5. 没有用户测试、没有部署、没有真实客服对话验证。
